# Q1Lens 버그 수정 기록 · 2026-11-22

최근 추가한 검증기, 파형 출력 모델, VS Code 확장, QBS 내보내기에서 12건을 재현하고 수정했다. 점검 기준은 `main`의 `37d55b8`과 당시 작업 폴더의 미커밋 변경이다. 각 항목의 수정 전 동작을 회귀 테스트로 확인했다.

## 프로그램 검증과 반례 재생

| 기능 | 수정 전 증상 | 수정 내용과 확인 결과 |
| --- | --- | --- |
| 두 소스의 RT 트레이스 비교 | 같은 `wait D`를 비교해도 한쪽에만 `@assume 4 <= D <= 8`을 쓰면 다른 쪽의 `D`가 미정이라 `unknown`이 됐다. | 입력 범위를 양쪽 소스에 적용한다. 예제의 다섯 값 모두에서 두 트레이스가 일치했다. |
| 시퀀서 간 정렬 | 프로젝트 입력 `D`를 시퀀서마다 독립적으로 바꿔, 같은 실행에서 한쪽은 4, 다른 쪽은 5인 반례를 만들었다. | 공유 입력의 가정들이 겹치는 범위에서 한 번 고른 값을 모든 시퀀서에 전달한다. 각 소스가 직접 선언한 `.DEF`는 해당 소스에서 결정한다. |
| 정렬 검사에서 트리거 전달 | `params.json`의 주소가 1이고 검사할 주소가 2이면, 프로그램은 주소 2를 검사하는데 트리거는 주소 1로 전달됐다. 정렬 차이가 있어도 `proved`가 나왔다. | 실행마다 해당 입력값으로 트리거 경로를 결정한다. 주소 2에 트리거가 도착하는 경우의 정렬 반례를 찾았다. |
| 소스 단언 검사에서 트리거 재생 | 입력 주소를 바꾸면 `wait_trigger`가 기다리는 주소와 재생에 사용하는 수신 주소가 달라졌다. | Concrete 재생에도 같은 입력을 적용한다. 주소 4와 5 모두 20 ns에 도착한 트리거를 받고 24 ns에 라벨에 도착했다. 주소 5의 종료 시각 29 ns가 `rt_time <= 28`을 위반하며, 반례가 해당 타임라인 이벤트를 가리키는 것도 확인했다. |

## 파형 출력

| 기능 | 수정 전 증상 | 수정 내용과 확인 결과 |
| --- | --- | --- |
| 기호 대기 시간이 있는 파형 | `wait T`의 큐 언더플로 여부를 확정할 수 없으면 표현 가능한 파형까지 `unavailable`로 표시됐다. | 큐 경고가 가리키는 원인을 확인하고 출력 구간에 필요한 시간식을 보존한다. `T=12`를 대입하면 파형 시작이 12 ns가 되고, 동기화 상대가 빠진 경우에는 출력이 미확정으로 남는다. |
| 트리거 뒤 첫 파형 | `wait_trigger 1,0`에서 40 ns에 트리거를 받으면, 다음 파형이 40 ns에 시작하는 것으로 계산됐다. | 대기 시간이 0인 패킷도 차지하는 4 ns를 트리거 도착 후에 반영했다. 출력 샘플은 Concrete 실행과 같이 43 ns까지 0이고 44 ns에 시작한다. |
| 조건부 반복의 이득과 위상 | 반복 경계에서 `play`를 건너뛰면 다음 반복에 적용할 이득이 사라지거나, 한 번만 적용할 위상 변화가 다시 적용됐다. | 건너뛴 패킷에서 유지할 설정과 소모할 설정을 구분한다. 압축된 3회 반복과 각 명령을 실행한 Concrete의 I/Q 샘플을 0–47 ns 구간에서 대조했다. |
| 원시 `fb_cmd`의 오프셋 적용 | 반복 안에서 `upd_thres`를 `fb_cmd 0x10`으로 쓰면 두 번째 반복의 오프셋을 놓쳤다. | 실행기가 기록한 설정 적용 여부를 읽어 두 명령 표기를 동일하게 처리한다. 오프셋 16384가 8 ns부터 정규화된 값 0.5로 나온다. |

## VS Code, 실행 엔진, QBS

| 기능 | 수정 전 증상 | 수정 내용과 확인 결과 |
| --- | --- | --- |
| VS Code 검증 결과 갱신 | 닫힌 `inputs.data`를 디스크에서 고쳐도 검증 결과가 갱신되지 않았다. 다시 Verify를 실행해도 이전 `Proved`가 남았다. | 기본 파일 감시 패턴 밖에 있는 프로젝트 입력 파일도 감시한다. 실제 VS Code에서 입력을 17에서 31로 바꾸면 `R0 == 17`에 대한 반례가 표시된다. |
| Hardware 탭의 수식 | 이득이 변하는 예제에서 `4096 + 4096 * #L0/32768`로 보여 나눗셈이 마지막 항에만 적용되는 것처럼 읽혔다. | 복합 분자를 괄호로 묶어 `(4096 + 4096 * #L0)/32768`로 표시한다. 이득, 오프셋, 주파수, 위상에 같은 표기 규칙을 쓴다. |
| 레지스터로 전달한 RT 인덱스 | 파형 인덱스 1024와 취득 bin 인덱스 16777216을 레지스터로 넘기면 시뮬레이터는 거부했지만 Concrete는 완료로 표시했다. Playback도 범위 밖 파형 인덱스의 `play` 이벤트를 기록했다. | 명령을 발행하기 전에 레지스터에서 읽은 값을 검사한다. 파형의 허용 최댓값은 1023, bin의 허용 최댓값은 16777215다. 범위 밖에서는 실행이 멈추고 해당 패킷을 발행하지 않는다. |
| QBS 컴파일 결과 내보내기 | `sequence`를 `__slots__`에 보관하면 시퀀서 프로그램이 누락됐다. dataclass가 부모 클래스의 슬롯에서 이득을 상속받으면 이득 설정만 사라지는 경우도 있었다. | 상속받은 공개 슬롯과 `sequence` 속성도 읽는다. 두 형태의 설정 객체로 Q1ASM을 내보내고 `.sequence.json`에서 파형 메모리와 정적 이득 `[0.5, 1]`을 확인했다. |

Python 3.12에서는 `quantify_core`가 사용 중단 예정인 `qcodes.utils.helpers`를 가져올 때 경고 1건이 발생했다.

### VS Code 테스트의 간헐적 시간 초과

첫 VS Code 전체 실행에서 실패한 단언을 여는 테스트가 90초를 넘겼다. 별도의 실행에서는 서로 다른 두 RT 트레이스를 여는 테스트도 같은 방식으로 시간 초과됐다. 당시 로그에는 대기하던 화면 요소가 남지 않아 최초 원인은 특정하지 못했다. 다음 실패에서 해당 요소를 식별할 수 있도록 Playwright의 기본 대기를 10초로 설정했다. 이후 새 VS Code 창에서 검증 기능 테스트 6개를 두 차례 실행해 모두 통과했다. 최종 전체 실행에서도 두 테스트가 각각 0.78초와 0.82초에 통과했다. 이 테스트 환경 변경은 위 제품 수정 12건의 집계에서 제외했다.

## 다시 검증하기

아래 명령은 개발 의존성과 Playwright Chromium이 설치된 Windows 작업 폴더를 기준으로 한다. 확장 테스트에도 같은 Python 환경을 사용한다.

```powershell
$env:PATH = (Resolve-Path .venv/Scripts).Path + ';' + $env:PATH
$env:PYTHON = (Resolve-Path .venv/Scripts/python.exe).Path
$env:Q1LENS_BROWSER_PYTHON = $env:PYTHON
$env:Q1LENS_VSCODE_TEST_VERSION = '1.147.0'
& $env:PYTHON -m pytest -q
Set-Location vscode-extension
npm.cmd test
npm.cmd run test:browser
npm.cmd run test:extension
```
