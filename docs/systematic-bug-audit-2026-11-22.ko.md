# 검증 판정과 타임라인을 전수 대조한 기록 · 2026-11-22

이 점검은 `main`의 `37d55b8`과 당시 작업 폴더의 변경을 대상으로 했다. [앞선 버그 수정 12건](bug-fixes-2026-11-22.ko.md)에 이어, 같은 입력에 대해 검증기의 판정과 독립적으로 계산한 실행 결과가 일치하는지 검사해 아래 8건을 수정했다.

## 어떤 버그를 찾았나

| 검사 대상 | 수정 전 재현 | 수정 후 결과 |
| --- | --- | --- |
| 레지스터 단언의 유효성 | 여러 시퀀서가 있는 프로젝트에서 도달하지 않는 라벨에 `R64 == 0`을 쓰면 `proved`였다. 유효 범위를 벗어난 비교값 `R0 == -1`도 통과했다. | 단언을 먼저 검증한다. 두 경우 모두 단독 실행과 프로젝트 실행이 같은 이유로 `unknown`을 반환한다. |
| 같은 라벨의 반복 방문 | 첫 방문에서 레지스터가 아직 준비되지 않으면 이후 방문의 명백한 위반을 놓쳤다. 첫 입력에서 읽을 수 없을 때 뒤 입력의 반례도 가려졌다. | 남은 방문과 입력을 검사한다. 예를 들어 `N=1`에서 읽을 수 없어도 `N=2`에서 `R0 <= 1`을 위반한 값 2와 그 명령을 보고한다. 읽을 수 없는 경우만 남으면 `unknown`이다. |
| RT 트레이스 비교의 공유 입력 범위 | 두 파일이 같은 외부 입력 `D`를 각각 4…8과 6…9로 제한하면 교집합이 있어도 비교가 중단됐다. | 공통 입력 6…8을 검사한다. 7에서 한쪽만 4 ns를 더 기다리는 예제의 첫 반례는 `D=7`이다. |
| 외부 입력과 소스 내부 상수의 이름 충돌 | 한 파일의 외부 입력 `D=4…6`이 다른 파일의 `.DEF D 8`까지 덮어써 두 프로그램이 같다고 판정했다. | `D=4`에서 4 ns와 8 ns의 차이를 재생한다. 파일 순서를 바꿔도 같은 차이가 나온다. |
| RT 패킷이 없는 프로그램의 종료 시각 | 고정 시작 시각으로 `stop 1`과 `stop 2`를 비교하면 반례가 명령 발행 시각인 0 ns를 가리켰다. | 종료 코드가 정해지는 완료 시각인 4 ns를 가리킨다. 앞에 `nop`를 1개 또는 2개 넣으면 각각 8 ns, 12 ns다. |
| 정렬 검사에서 유효하지 않은 트리거 주소 | 주소 범위 0…1을 확인할 때, 주소 0의 오류로 탐색을 멈춰 유효한 주소 1의 정렬 차이를 놓쳤다. | 주소 1에서 두 시퀀서가 204 ns와 208 ns에 종료하는 반례를 찾는다. 유효한 입력에서 차이가 없더라도 주소 0이 미해결이면 `unknown`이다. |
| 소스 단언과 큐 검사에서 유효하지 않은 트리거 주소 | 주소 0…1의 양 끝을 먼저 검사하다가 주소 0에서 전체 검사를 종료했다. | 주소 1에서 `R0=1`, RT 시각 5 ns의 단언 위반을 각각 재생한다. 시작 지연이 4 ns일 때는 4 ns의 큐 언더플로도 찾는다. 주소 0이 미해결이므로 주소 1을 ‘최초 실패’로 표시하지 않는다. 주소 14…16에서는 유효한 14…15까지만 안전 구간으로 표시한다. |
| 출력 단언에서 명령의 레지스터 피연산자 | 잘못된 이득을 다음 줄에서 덮어쓰거나, 취득 bin이 반복 둘째 회차에서 범위를 벗어나도 `no_clip`이 `proved`로 나왔다. | 출력 샘플로 남지 않는 명령에서도 발행 시점의 허용 범위를 확인한다. 유효성을 입증할 수 없으면 `unknown`이다. 정상 경계값에서는 기존 증명이 통과한다. |

### 잘못된 출력 증명을 재현하는 최소 예제

```asm
;@assume 32767 <= G <= 32768
;@assert no_clip
move G,R0
nop
set_awg_gain R0,R0
set_awg_gain 0,0
upd_param 4
stop
```

`G=32767`이면 프로그램은 완료한다. `G=32768`이면 첫 `set_awg_gain`에서 Concrete 실행이 중단돼 다음 줄에 도달할 수 없다. 수정 전에는 최종 이득 0만 보고 전체 입력 범위가 안전하다고 판정했다. 현재 `q1lens verify`는 같은 예제에 `unknown`과 종료 코드 2를 반환한다. 같은 경계 검사를 이득·오프셋, 일반·디지털·TTL 취득의 bin 인덱스, 래치 활성화 플래그에 적용했다. 매회 같은 합법적인 bin을 다시 설정하는 10만 회 반복은 명령 검사 예산 50에서도 `proved`다. [출력 단언 회귀 테스트](../tests/test_output_properties.py)

## 어떻게 대조했나

| 대상 | 독립적으로 계산한 기대값과 확인한 항목 |
| --- | --- |
| 레지스터 단언 | 미기록·쓰기 대기·읽기 가능이라는 세 초기 상태와 부호·32비트 경계 입력을 조합했다. 24개 실행에서 Q1 코어를 한 명령씩 진행해 라벨 방문 72회의 값을 기록하고, 단독 및 프로젝트 검증기가 가리킨 방문 순번과 값을 맞췄다. [단언 테스트](../tests/test_q1timeline_verification.py) |
| 정렬 | 트리거 도착 8·9·10·11 ns와 상대 시퀀서의 대기 8·12 ns를 조합한 8개 프로젝트를 만들었다. 각 프로젝트의 공유 대기 4·5·6 ns 및 트리거 유무에 대해 분기 조건과 체크포인트 시각을 직접 계산하고, 최초 차이가 나는 입력·소스 줄·이벤트 시각을 대조했다. [정렬 및 비교 테스트](../tests/test_q1timeline_verification_compare.py) |
| 파형 | 반복 1·2·3회 × 조건부 건너뛰기 유무 × 트리거 후 대기 0·4 ns의 12가지다. 40 ns에 트리거가 오면 두 대기값 모두 첫 파형은 44 ns에 시작한다. 첫 파형부터 마지막 무출력 구간까지 이득과 위상으로 직접 계산한 I/Q 값과 1 ns마다 비교했다. [파형 테스트](../tests/test_q1timeline_symbolic_output.py) |

파형 테스트에서 실제 트리거가 들어간 원본 프로그램은 Concrete로 실행했다. 공개 기호 분석 API는 외부 도착 시각을 받지 않으므로, 같은 반복 본문에 확정된 시작 시각 44 ns를 대입해 압축 파형을 대조했다. 이 12개 조합의 현재 동작은 모두 기대와 일치했다. 종전 버그를 격리된 실행에서 되살렸을 때는 0 ns 대기 처리 오류가 6개 조합에서, 건너뛴 회차의 이득 누락이 4개 조합에서 검출됐다.
